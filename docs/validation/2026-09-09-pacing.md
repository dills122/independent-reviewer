# Rate-limit cooldown and pacing — 2026-09-09

## Implemented

- HTTP/provider 429 uses a randomized 5–10 second retry delay when Retry-After
  is absent or invalid. Valid hints retain precedence; hints beyond the existing
  30-second automatic-retry wait limit stop that retry rather than retrying early.
- A shared in-process ProviderCallPacerV1 pauses new calls for the affected model
  across batch workers. Cooldown applies even after a review exhausts its retry.
  Existing in-flight requests continue. Retry adapters retain the same coordinator.
- Optional minimum spacing between request starts defaults to zero. It is not a
  mandatory sleep after every successful response. Separate CLI processes do not
  share in-memory state; the comparison uses concurrent runCliV1 invocations in
  one process with an explicitly shared coordinator.
- Maximum one provider retry, existing model/allowlist/privacy policy, 180-second
  network timeout, and $0.02 per-review admission ceiling remain unchanged.

## Evidence behind the policy

[OpenRouter](https://openrouter.ai/docs/api_reference/limits) recommends backoff
and honoring Retry-After. [DeepInfra](https://docs.deepinfra.com/account/rate-limits)
documents busy-model 429s below account concurrency limits and recommends waiting.
[OpenAI's Cookbook](https://developers.openai.com/cookbook/examples/how_to_handle_rate_limits#proactively-adding-delay-between-requests)
describes proactive pacing for repeatedly rate-limited batch workloads. The
5–10 second setting is an engineering starting point, not a provider guarantee.

## Verification and live comparison

All 193 existing tests pass through npm run check; git diff --check passes.
A direct timing check observed shared waits at 81/122/163 ms with an 80 ms
cooldown and 40 ms minimum spacing. A waiting worker also honored an extended
cooldown (122 ms elapsed for a 120 ms target).

Two existing fixtures ran under each pacing setting, two workers per group.
Both groups used the new 429 cooldown. No manual reruns occurred.

| Minimum start spacing | Fixture | Result | Calls | Seconds |
| --- | --- | --- | --- | --- |
| 0 seconds | Clean multi-file | READY, no findings | 2 | 61.7 |
| 0 seconds | Cross-file defect | Repeated provider 429; retry exhausted | 3 | 69.3 |
| 2 seconds | Clean multi-file | Repeated provider 429; retry exhausted | 3 | 50.1 |
| 2 seconds | Cross-file defect | Preliminary response contained duplicate finding IDs | 1 | 65.5 |

Observed retry waits included 7.220 and 9.956 seconds. The spaced group's initial
request starts were 2.001 seconds apart. Nine calls reported $0.001538671,
excluding four failed calls with unknown cost.

This tiny sequential comparison does not establish a causal effect of spacing:
provider conditions vary, and one failure was model-output validation. It gives
no evidence to enable a blanket delay. Keep optional spacing at zero by default
while retaining the documented cooldown/recovery behavior. Neither waits nor
retries guarantee availability when both allowed providers reject requests.
